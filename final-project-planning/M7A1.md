# Midterm Reflection Journal

## Reflection on the Full Stack Part of TindahanTrack

This journal is more focused on what happened when TindahanTrack transitioned from a front-end interface to a full stack JavaScript application, as I've already completed a prelim reflection earlier in the course.

The React side was initially clearer to understand as I could see all the changes in real time. Shared data like items, transactions, cart contents, loading state and current theme is owned by the App.jsx. The larger sections are arranged on pages and repeated sections like product cards, summary cards, category filters, and form fields are handled by small components. This structure proved particularly useful when implementing the Quick Cart as the state of the cart must be consistently managed across Inventory and the checkout drawer, and product data was not to be duplicated.

When it comes to styling, I also learned that it isn't all about picking a color. I began to apply the CSS custom properties to the main color, warning color, surfaces, text, spacing, shadows and radii. The 8px spacing scale helped to make the decision of the padding and gaps easier without looking like each part is separated. I also learned that responsive work isn't simply shrinking desktop layouts! The mobile version is also equipped with a fixed bottom navigation, a 2 column product grid, touch friendly controls and finally the mobile cart drawer that has to leave the checkout button above both the app bottom navigation and the Android safe area. Identified and resolved an actual problem where the mobile bottom navigation was covering over the Complete Sale button.

Backs were harder, but got the project real. Used Express to create routes for inventory items, stock updates, image uploads, recent transactions, and analytics. I learned what the purpose of parameterized PostgreSQL queries is: Values like product names and product IDs are sent as arguments, not as part of the SQL string. When deducted from a stock, I did a database transaction to ensure that the item update and transaction log are considered a single unit. In the case of a sale that fails, the database can roll back without leaving the inventory count "changed" without a matching sales record.

It was when I connected React to Express that I had a better understanding of REST. Based on the action, the React client makes a `GET`, `POST`, `PUT`, `PATCH`, and `DELETE` requests. The server returns a JSON message and the client changes its state based on the message received from the server. I've kept the browser `localStorage` Demo Mode as it was not possible to run the Node server on GitHub Pages. That made me consider 2 data paths: one is the live path, which has Express, Neon PostgreSQL, and a temporary ngrok tunnel and the other is the demo path, which is the same user flows with inventory and transactions stored in localStorage.

One workaround that I found was the browser warning from ngrok. The app could get to the tunnel, and although a `GET` request to the tunnel returned an HTML warning page, instead of JSON, the inventory looked as if it were empty. I learnt how to be discerning about the actual response and not take everything that looks like an API response at face value. So, the solution was to propagate the skip-warning header on all API calls from ngrok. The other test was to test the Capacitor Android wrapper. The current Vite `dist` bundle and the current ngrok URL were required for the Android build to be able to connect to the live API. This clarified the connection between the environment variables, builds and native assets.

I used AI as a coding assistant to plan, debug and review changes, but had to cross-check suggestions against the running app. This can be done in many ways, such as checking that the ngrok header was required for all requests, observing that the mobile checkout overlap is an issue on a physical device, and securing secrets from client environment variables. The big lesson I got from it is that a working interface is just one aspect of a complete project. Now I need to know where state lives, what happens when I request it changes state, what happens when it fails and returns to the UI, and what happens when it doesn't have the live server available so the app remains usable.
